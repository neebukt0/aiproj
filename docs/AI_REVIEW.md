# AI_REVIEW — аудит безопасности и корректности

Повторный аудит выполнен 2026-11-11 после исправления недочётов. Проверялись
код, конфигурация, тесты (`42 passed`), сборка фронтенда и ручные запросы к API.

## 1. Аутентификация и авторизация
- JWT HS256 (`python-jose`): access 15 мин, refresh 7 дней. Refresh хранится в
  `refresh_tokens` (`jti`, `user_id`, `revoked`, `expires_at`).
- `get_current_user` требует Bearer-токен, проверяет подпись и срок; невалидный
  или просроченный токен → `401` (ранее был `500`).
- Refresh проверяет `revoked` и `expires_at`; просроченный/отозванный токен → `401`.
- Logout принимает только refresh-токен текущего пользователя; чужой токен → `403`.
- Неактивный пользователь (`is_active=false`) не может войти (`403`) и не может
  использовать ранее выданный access-токен (`403`).
- Публичная регистрация всегда создаёт роль `client` и игнорирует поле `role`
  (защита от privilege escalation). Staff-пользователи создаются только
  администратором через `POST /api/admin/users`.
- Проверки ролей на backend: клиент видит только свои брони и может отменять
  только свои; подтверждение/завершение — `employee/admin`; панель, логи,
  отчёты — staff; управление пользователями, удаление ресурсов — `admin`.
- Администратор не может заблокировать, удалить или понизить сам себя.

## 2. Пароли и секреты
- Пароли хэшируются bcrypt (passlib), не логируются и не возвращаются в ответах.
- Пароль: минимум 8 символов, максимум 72 (ограничение bcrypt).
- Конфигурация читается из env (`backend/.env`, `load_dotenv` в `config.py`);
  `.env` исключён из git, в `.env.example` только заглушки.
- При использовании дефолтного `SECRET_KEY` приложение пишет предупреждение в лог.

## 3. Бронирования, hold и конкуренция
- Удержание: `held_until = now + 10 min`. Активные брони — `status in
  (created, confirmed)` и `held_until > now`.
- Конфликт интервалов: `start_at < new_end && end_at > new_start` при активной
  брони → `409`.
- `end_at <= start_at` → `400`.
- Атомарная блокировка ресурса: `find_one_and_update` с `upsert=True` на
  `bookings_locks`; `DuplicateKeyError` трактуется как занятость; истёкшие
  блокировки (>10 мин) освобождаются повторной попыткой.
- Проверено тестами: 10 параллельных запросов на один слот → ровно 1 успешная
  бронь, остальные `409`; освобождение после истечения hold.
- Участники мероприятия проверяются на существование; дубликаты `participant_ids`
  устраняются; список участников доступен владельцу брони и staff.

## 4. Статусы и журналирование
- Переходы: `created→{confirmed,cancelled}`, `confirmed→{completed,cancelled}`;
  недопустимые/терминальные → `409`.
- Смена статуса атомарна: `find_one_and_update` по `_id` и текущему `status`;
  при конкурентном запросе второй получает `409`.
- Если запись в `status_logs` не удалась, выполняется компенсирующий откат
  статуса, чтобы не потерять журнал.
- Каждое изменение фиксируется в `status_logs` (`booking_id`, `from_status`,
  `to_status`, `changed_by`, `changed_at`, `note`).

## 5. Данные, индексы, отчёты
- Индексы создаются идемпотентно в lifespan приложения и в seed:
  `users.email` (unique), `bookings(resource_id,start_at)`,
  `bookings(user_id,start_at)`, `status_logs(booking_id,changed_at)`,
  `refresh_tokens.expires_at`, `booking_participants.booking_id`.
- Все datetime, отдаваемые API, нормализуются в timezone-aware UTC.
- Отчёты: валидация периода (`end_at > start_at` → иначе `400`), агрегация
  MongoDB по периоду/ресурсу, CSV через `StreamingResponse` с
  `Content-Disposition: attachment`. Дубли строк в отчёте устранены.
- Ошибки MongoDB обрабатываются общим обработчиком → `503` без утечки деталей.

## 6. Frontend
- Access-токен читается напрямую из `localStorage`, без гонки инициализации.
- При `401` выполняется одна попытка refresh на все параллельные запросы; при
  неудаче сессия очищается и выбрасывается `auth:unauthorized`.
- Защищённые маршруты (`/my`, `/panel`, `/admin`, `/reports`, `/logs`) закрыты
  компонентом `ProtectedRoute` с проверкой роли.
- Регистрация больше не предлагает выбрать роль.
- Удалены неиспользуемые шаблоны Vite (`App.jsx`, `App.css`, `src/assets/*`,
  `public/icons.svg`).

## 7. Остаточные риски/ограничения
- В локальном окружении нет валидной MongoDB: тесты идут на `mongomock-motor`.
  Реальный запуск seed/API требует корректного `MONGODB_URL`.
- `mongomock-motor` не полностью эмулирует MongoDB (например, naive datetime),
  поэтому в коде есть нормализация tz-aware.
- Записи `bookings_locks` не удаляются фоново, но освобождаются по таймауту при
  следующей попытке; фоновая очистка по SPEC не требуется.
- Для продакшена: заменить `SECRET_KEY`, ограничить CORS конкретными origins,
  настроить HTTPS, ротацию refresh-токенов и реальную БД.

## 8. Итог
Ключевые требования SPEC (JWT/роли, hold 10 мин, конфликт `409`, атомарность
конкурентного бронирования, журнал статусов, отчёт/CSV, участники мероприятия)
реализованы и покрыты 42 автоматическими тестами. Найденные при аудите
блокирующие и security-недочёты устранены; для деплоя требуется валидная
конфигурация БД и секретов.
